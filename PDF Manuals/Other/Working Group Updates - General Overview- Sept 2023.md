Summary of UPI Changes
• The scope includes Credit, Rates, Foreign Exchange, and Equities [[Asset]] classes (A compliance date for Commodities has yet to be 
announced and is out of scope.)
• The changes will apply to the [[CFTC]], [[SEC]] and Canada jurisdictions. 
• Addition of UPI field for submission/reporting for Trade State, PPD and Valuation messages
• Addition of UPI related validations on approximately ~17 fields
• ~56 UPI Data Elements from ANNA-DSB to be included on Trade State Reports (TSR) and 3 new fields for Public Price Dissemination 
(PPD) Reporting
• Current product fields will be reported until a new submission with UPI is submitted and processed
• Firms are expected to update open positions for UPI by the January 29th Compliance date
Summary of Part 43 (PPD/LNOFS) Changes
Deferred: Date TBD
• The changes associated with this update will impact all five reportable [[Asset]] classes (credit, interest rates, equities, commodities, and 
FX) 
• LNOFS will impact Trade State and PPD for [[CFTC]] submissions.  
• Post Initial Cap Sizes will impact PPD for [[CFTC]] and [[SEC]] submissions.
• New [[Asset]] class groupings will be applied based on the 2020 [[CFTC]] Part 43 regulations and thresholds will be based on the final 
thresholds published to the [[CFTC]] website in April 2023. 
Other Changes
The [[CFTC]] has made additional changes to current fields in the latest Technical Specification and Guidebook that will impact all [[Asset]] 
classes and will be implemented for January 2024

Message Validation/Responses

Specifications), there will be no changes to the [[BASIC]] process by which messages are validated for NOA GTR.  The validation process

•Schema Validation (validates that the message is formatted correctly so that it can be parsed)
•Permission Validation (validates that the submitter has permission to submit the message)
•Core Validation ([[BASIC]] global validations of key fields as defined in the Message Specifications)
•Jurisdictional Validation (validations specific to each jurisdiction as defined in the Message Specifications)

Trade Identifier
Trade Uniqueness
A UTI is required for all new trades submitted for [[CFTC]], Canada and [[SEC]] reporting after 
the go-live (using Action Type “NEWT”). 
Trades that are live prior to the Re-Write go-live can continue to be submitted using the 
Trade Identifiers (USI, UTI, or Both UTI and USI). A USI cannot be added to trades with UTI 
only.
For Trade State (P45) reporting AND Public Price Dissemination (P43) reporting, the 
uniqueness of a trade will be determined by the concatenation of 
UTI (UTI [[ID]] prefix + UTI [[ID]] value) + USI (USI [[ID]] prefix + USI [[ID]] value) + Trade Party 1 
([[ID]] Type + [[ID]])

Notes related to P45 (Trade State):
• The first submission for a trade must be NEWT. 
• No action type submission is required to Expire a trade.  The 
end-of-day process within the GTR will remove expired trades 
from the Trade State Report (TSR) on the day after expiration 
(as it does currently).  In the state diagram below, this process 
will logically move trades from “Open” to “Expired” status.  
• MODI, CORR, VALU, and MARU submissions to expired or 
terminated trades are allowed so participants can correct the 
historical record.  Submitters are responsible for ensuring 
relevant dates are accurate (there are no validations 
performed to ensure the submissions are appropriately 
“historical”).
• When a trade is TERM, EROR, or PRTO, it will not appear on the Trade State Report on the day of the corresponding submission. Once a trade is 
Terminated or Errored, the only way for it to appear again on the TSR is to submit a REVI message (where the expiration date is >= today).
• Once a trade has been Transferred Out (to another repository), the only way for it to appear again on the TSR is to submit a message with action type = 
NEWT and event type PTNG (with an expiration date >= to today) to port the trade back into the GTR.

[[collateral]] Messages ([[CFTC]] only)
• [[collateral]] valuations need to be submitted to the GTR using a separate [[collateral]] Valuation message. These must be submitted 
using the harmonized CSV [[collateral]] template (details on the message layout and validations can be found in the Message 
Specifications).  
• These messages can only be submitted via Web Upload or SFTP (they will not be accepted via MQ). 
• Validations will be performed as specified in the Message Specifications.
• There will not be support for the “[[collateral]] link” messages currently used in other jurisdictions.  Trade state or Trade Valuation 
submissions should be used to populate the relevant portfolio code(s) on each trade.  
Valuation Messages ([[CFTC]] and Canada)
• Valuations will only be accepted if there is a base trade which matches the valuation submission (UTI/USI + Trade Party 1 + Trade 
Party 2 + Jurisdiction must match). Any valuation submitted on a position without a base trade will be rejected (NACKed).
• Valuations that are submitted on inactive trades (expired or terminated) will not “revive” the trade (i.e. they will not re-open the 
trade such that it will appear on the Trade State Report). In this scenario the valuation submission will be reported as activity in 
the Valuation Activity Report but will not be reported on Trade State Reports for both the regulators and participants. 
• [[collateral]] IM/VM portfolio codes will be merged from Trade Valuation submissions from the Valuation submission with the most 
recent valuation timestamp.  If no Valuation message has ever been received into the GTR for the trade, the values from the 
Trade State submission will be reported on the TSR.

Report Types
Type Description
Trade State 
Report
• Contains the latest trade state for all open trades for each unique trade that contains the relevant jurisdiction value in the R eporting destination data 
element. 
• This report is created per [[Asset]] class per jurisdiction.
• Trades which expire on or after reporting date are included.  
• Trades which have been submitted with action type TERM or EROR (and not subsequently revived) or have been submitted with action type PRTO (and 
not ported back in) are not included (even if their expiration date is in the future).
• Trade valuation data is merged onto this report.  [[collateral]] valuation data is NOT merged onto this report.
Trade Activity 
Report
• Contains all successful submissions for trade state (not PPD/RT, valuation and [[collateral]]) message types that contain the relevant jurisdictional value in 
the Reporting destination data element.
• This report is created per [[Asset]] class per jurisdiction.
Submission 
Report
• Contains all the successful (ACK) and unsuccessful (NACK) submissions submitted by the client as well as those submissions made on their behalf. 
• This report is created per [[Asset]] class per jurisdiction.
• There will be a separate [[collateral]] submission report.
Public Price 
Status Report
• Contains all the successful PPD submissions received for the reporting date, as well as PPD submissions which may have been received on a previous 
date, but which were disseminated on the reporting date. 
• The PPD status report includes transformed (rounded, capped, scaled) values as well as original values submitted.
• This report is created per [[Asset]] class per jurisdiction.
Valuation Activity 
Report 
• Contains all successful Valuation submissions processed for the reporting date.
• This report is created per [[Asset]] class per jurisdiction.
• It will be provided to submitters, reporting parties, and regulators.
[[collateral]] Activity 
Report
• Contains all successful [[collateral]] Valuation submissions processed for the reporting date.  
• This report will be produced per jurisdiction (currently [[CFTC]] only).
• This report is not produced per [[Asset]] class as the content is not [[Asset]]-class specific.
• It will be provided to submitters, reporting parties, and regulators.
Trade State Allege 
Report
• Contains the latest trade state for all open trades for each unique trade that contains the relevant jurisdiction value in the R eporting destination data 
element where the report recipient is named as “Trade Party 2” 
• This report is created per [[Asset]] class per jurisdiction.
• Trades which expire on or after reporting date are included.  
• Trades which have been submitted with action type TERM or EROR (and not subsequently revived) or have been submitted with action type PRTO (and 
not ported back in) are not included (even if their expiration date is in the future).
• Trade valuation data and [[collateral]] valuation data are NOT merged onto this report.
