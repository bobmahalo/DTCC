INTRODUCTION 
Executive Summary 
As part of reimagining the evolution of the financial services industry, Project Ion development began in 2019 
as a proof of concept (POC) to test new clearance and [[settlement]] functionality and the suitability of Distributed 
[[Ledger]] Technology (DLT). The Project Ion POC led to the development of a prototype in a stand-alone 
environment that allowed members to interact with the platform to test out the complex features. Positive client 
feedback on the prototype prompted the proposal of an Ion production parallel (Ion MVP1) designed to migrate 
portions of the Project Ion prototype system into the [[DTCC]] production environment. The Project Ion MVP 
provides participating members with an opportunity to have certain deliver order transactions routed to the Ion 
platform for parallel processing using a new DLT-based system.  
The vision for Project Ion in its end state has the potential to be an integral part of the overall modernized 
clearing and [[settlement]] applications. This will be accomplished through multiple iterative development phases 
that will closely coordinate with industry stakeholders.  
Project Ion  
                   
Project Ion’s goal is to demonstrate the DLT capabilities for a subset of eligible transactions. Eligibility is 
limited to participating members’ day & night deliveries and receives in [[Equity]] [[securities]] using Reason 
code 30. 
[[DTC]]’s current [[settlement]] systems (Classic [[DTC]]) will continue to remain the authoritative source for 
the time being. 
There are several key components to the Project Ion platform: 
Network Architecture  
[[DTCC]] will: 
a. Establish the DLT network infrastructure, host all nodes, and set the standards and guidelines for the 
ecosystem. 
b. Be responsible for provisioning and introducing [[participant]] nodes on the network.  
c. Serve as the network operator and serve as the notary for all transactions. 
d. Support participants accessing data on their nodes through APIs and user interfaces with [[DTCC]].  
e. Provide event messaging for all events that occur on the DLT (Propose, Approve, Settle)

Transaction Capture  
As deliver order instructions are submitted to [[DTC]], [[DTC]] will automatically route them through the Project Ion 
flows providing clients with a “hands-off” approach for routing transactions through. [[DTC]] is also introducing a 
new API for deliver order input. The new capability is not limited to Ion-eligible transactions, but eligible activity 
input through the new API is subjected to the Project Ion flows automatically. 
Reflection of [[settlement]] Status  
[[DTCC]]’s Classic [[settlement]] systems remain the authoritative source for [[settlement]] processing. Each time an 
Ion-eligible transaction status changes in Classic [[DTC]], messages are passed back to the Project Ion platform 
and eligible statuses trigger processing on the Project Ion [[Ledger]]. The Project Ion platform serves as a parallel 
book and infrastructure for these limited bilateral transactions demonstrating that eligible [[settlement]] statuses 
can be processed through the Project Ion MVP platform. 
[[settlement]]  
The primary focus of initial releases of Ion is to demonstrate DLT principles reflected through 3 stages in Ion 
Distributed [[Ledger]]: Initiation (“Propose”), Approval (“Approve”), and Movement of [[securities]] (“Settle”).  
Propose: Deliver Orders submitted on [[settlement]] day (“XPRS”) are immediately proposed on the [[Ledger]].  For 
future dated / night [[DO]], proposal on the [[Ledger]] does not occur until [[settlement]] day when the instruction has 
been authorized by the Deliverer and submitted for receiver approval (“RSUB”) / sent to [[settlement]] (“SUBA”).  “  
Approve: Receivers must approve all deliver orders. This can be an explicit action initiated by the client in 
Classic (“RAUT”) or an implicit approval given when a [[DO]] is not eligible for RAD in the Classic system.  
Settle: A Deliver Order settles in Ion DLT once it passes risk controls and settles in Classic (“MAKD”).

Project Ion DLT Platform 9 
PROJECT ION DLT PLATFORM 
Project Ion is a distributed-[[Ledger]]-driven service offering. The platform consists of a permissioned network 
of DLT nodes, which is centrally managed by [[DTCC]]. Each Project Ion [[participant]] node has a [[Ledger]] 
with information of their bilateral transactions. In future phases, clients may host their own nodes with [[DTCC]] 
providing standards and guidelines. 
 
 
DLT Basics 
• Project Ion platform enforces [[DTCC]] business logic related to Project Ion [[settlement]] through smart 
contracts. 
• The deliverer, receiver, and [[DTCC]] are always guaranteed to see the exact same version of data of their 
bilateral transaction. Although the same version of the transaction exists for all parties, users are only able 
to see the information they are allowed to see.  
• Each Project Ion [[participant]] has a node at the [[DTC]] Legal Entity level with multiple child [[participant]] 
accounts hosted on that node, partitioned as needed.  
• Project Ion participants agree on transactions by signing transactions digitally. For the current Project Ion 
scope, [[DTCC]] will host the [[participant]] nodes and conduct the digital signatures on behalf of the 
participants.  
• Communication is peer to peer and only on a need-to-know basis—no global broadcasts.

Project Ion Network Architecture 
The [[DTCC]] Project Ion distributed [[Ledger]] network is comprised of several key components.  
 
 
• Network Map Service - Network map services act as a directory indicating the location of each one of the 
nodes and their information. 
• Notary - Non-validating notary that will ensure unique consensus by ensuring states are only used once 
on a given transaction. 
• [[DTCC]] node - [[DTCC]] node to initiate transactions and store transaction information, including participants 
who are not part of the Project Ion MVP. 
• [[DTCC]] Observer node - Observer nodes enable data redundancy on [[DTCC]] nodes 
• [[participant]] node - [[participant]] nodes are at the Legal Entity level, with a subset of accounts. 
• Smart Contracts - These will be leveraged as a core component of the DLT architecture to encapsulate 
business rules and logic. These will be enhanced as Project Ion evolves. 
 
Network Architecture – Future Expansion  
In future phases, [[DTCC]] will have an evolving role with the DLT network. While initially [[DTCC]] hosts all nodes 
and is establishing standards and guidelines, in future phases participants may host their own nodes.

Project Ion Output API  
The Project Ion API provides users the ability to query and view their instructions as they progress through the 
[[settlement]] lifecycle. Firms can customize and run instruction queries, giving them the ability to request 
information based on their exact needs. The following is currently available: 
• Ability to retrieve a single instruction identified by primary key (instruction [[ID]]). Details about the 
instruction will be returned, including current Classic [[settlement]] status as well as DLT status.  In 
addition, Ion and Classic events associated with this instruction may optionally be returned . 
• Ability to query instructions using various criteria, with matching instructions returned synchronously 
or asynchronously, depending on number of instructions meeting the search criteria.   
See the [[DTCC]] API Marketplace for details (https://developer.[[DTCC]].com/) .

Glossary 20 
GLOSSARY 
The following are general terms related to Ion. Because Ion is part of an enterprise- wide standardization of 
data element names across [[DTCC]], some local field names have been modified to reflect the broader standard.  
 
Business Term Description 
Instruction [[ID]] 
Reference number assigned to an instruction by a [[DTCC]] application. It is used 
to uniquely identify a [[settlement]] instruction within [[DTCC]]. This is also known as 
the IMS TID in Classic systems. 
Sender Instruction Reference [[ID]] 
Value supplied by a client on their instruction to uniquely identify that transaction 
for tracking and reconciliation purpose. This is also known as Sender Reference 
Number in Classic systems. 
Instruction Status Code Current state of the transaction being processed by [[DTC]] [[settlement]]. This will 
reflect the same values as in Classic systems today, such as RAUT or MAKD. 
Account [[ID]] 
Assigned identifier that represents the account. When retrieving information, the 
Account [[ID]] is always the side that requested the data, which may be the 
deliverer or receiver, as indicated by the Account Role Code. 
Account Role Code Identifies whether the account provided on the transaction represents the 
deliverer or receiver of [[shares]] in an instruction. 
Contra Account [[ID]] Assigned identifier that represents the counterparty of an instruction. 
Account Customer [[ID]] 
Identifier of the customer account as it is known on the Account [[ID]]’s books. 
Note 
The Account [[ID]] may be the deliverer or receiver as indicated by the Account Role 
Code. This is also known as Deliverer or Receiver Account in Classic systems. 
Contra Customer [[ID]] 
Identifier of the customer account as it is known on the Contra Account [[ID]]’s 
books. 
Note 
The Account [[ID]] may be the deliverer or receiver as indicated by the Account Role 
Code. This is also known as Deliverer or Receiver Account in Classic systems. 
Third Party Account [[ID]] The unique identifier (as entered by the Deliverer) of a third party of the 
instruction 
[[CUSIP]] [[ID]] A nine-character alphanumeric code that identifies a North American financial 
security for the purposes of facilitating clearing and [[settlement]] of trades.

Business Term Description 
[[settlement]] Date 
Month, day, and year on which the parties to the transaction mutually agree to 
settle the trade, as entered on the instruction by the party initiating the 
instruction. 
Instruction Quantity 
Total quantity of a financial instrument, as specified in a [[settlement]] instruction, 
that will be exchanged (delivered/received) between the two parties at the time 
of [[settlement]]. 
Instruction Amount 
Total amount of money that a receiver or deliverer of financial instruments will 
pay or be paid (respectively) in exchange for the financial instruments on a 
particular transaction at the time of its [[settlement]]. 
Instruction Reason Code Specific and clarifying reason as to the cause of a particular [[settlement]] 
instruction entered by the client initiating the instruction. 
Instruction Type Code 
Type of transaction being executed on [[DTC]]’s [[settlement]] system, e.g. "26" 
Delivery Order. In Classic system, this is known as Activity Code. It will reflect 
the same values as in Classic today. 
Instruction Effective Processing Date Business date that the transaction is being processed on [[DTC]] books and 
records. This term is also synonymous with delivery date. 
Deliverer Authorization Type Code Type of transaction being executed on [[DTC]]'s [[settlement]] system. In Classic 
system, this is known as Transaction Type. 
Instruction Source Code Identifies the originating source of the instruction being processed by [[DTC]] 
[[settlement]]. This will reflect the same values as in Classic systems today. 
Instruction Comment Text Freeform text field to hold any client-entered comments included on an 
instruction. 
Settle Today Only 
Used to instruct [[settlement]] on a specific date or until it settles across multiple 
dates. If the indicator is on, the transaction is not reintroduced regardless of the 
[[participant]]'s drop profile. If the indicator is off, the transaction is reintroduced 
regardless of the [[participant]]'s drop profile. If the indicator is not supplied, the 
transaction is either reintroduced or not based on the participants drop profile. 
Due Bill Carried Specifies whether due bills are carried on the issue or are not carried on the 
issue.
