OVERVIEW 
Universal Trade Capture (UTC) is a trade recording and validation application that communicates through 
messages with marketplaces, exchanges, clearing firms, and service providers. This document provides an 
interactive messaging specification for all inputs to and output from the UTC application. The Financial 
Information Exchange (FIX) Protocol is utilized as the messaging standard to submit and receive trade capture 
information from UTC. 
For more information about the UTC file formats and other documentation, visit the Universal Trade Capture 
(UTC) page available on the [[DTCC]] Learning Center at: https://dtcclearning.com/products-and-
services/equities-clearing/universal-trade-capture-utc.html

UTC Overview and Service Features 
In 2011, the UTC initiative consolidated and modernized the trade capture reporting process. In doing so, UTC 
created a single validation and reporting engine for [[NSCC]]’s four retired legacy trade capture systems 
(Correspondent Clearing (CORR), [[Over-The-Counter]] ([[OTC]]), [[New York Stock Exchange]] ([[NYSE]]) and Regional 
Interface Operation (RIO)). UTC also introduces a standardized input record from all marketplaces while 
continuing to support trade submission using proprietary formats. 
The UTC application validates and reports trades in near real-time, allowing clearing firms to run real-time or 
intraday reconciliation processes. Providing normalized, near real-time data also enables firms to enhance their 
own internal risk management operations. This document outlines and defines UTC’s transaction processing 
and reporting capabilities.

Features and Benefits 
Avail of the following UTC features and benefits: 
• Near real-time contract reporting – UTC validates trade input and sends output to clearing firms in 
near real-time. This allows firms to accelerate their purchase and sales processes. 
• Common format for all trade capture input and output – UTC has introduced standardized near 
real-time message-based output to clearing firms as a FIX standard message using MQ or the FIX 
engine. UTC’s ability to normalize, or standardize, data into a common output format will eliminate the 
need for firms to run their own internal conversion programs or outsource the function to third parties – 
reducing the cost of the post-trade process. To ensure maximum flexibility, the UTC system can 
accept, process and provide output in both the new format as well as in the legacy formats for both 
clearing firms and marketplaces.  
• Intraday master file updates – More frequent master file updates reduce firms’ wait time for rejects. 
UTC reports rejects earlier in the day by revalidating pended rejects intra-day, when master files are 
updated. Firms may also elect to receive pended reject messages throughout the day.

Clearing Firm Submissions 
[[NSCC]] allows clearing firm submission in the scenarios outlined below. Each is provided for reference.  
Correspondent Clearing Service 
The Correspondent Clearing Service may only be used in the following situations: (1) to accommodate a 
clearing firm with multiple affiliate accounts that wishes to move a position resulting from an “original trade” in 
the process of clearance from one affiliate account to another, and (2) to accommodate a clearing firm that 
relies on its Special Representative to execute a trade in a market that the clearing firm is precluded from due 
either to membership requirements or applicable [[regulation]], in order that the resulting position be moved from 
the Special Representative to that clearing firm. 
Qualified Special Representative Market 
A qualified special representative (QSR) is a special representative who exhibits one of the following: 
• Operates an automated execution system where it is always the contra side to each transaction. 
• Has a parent corporation or affiliated corporation that operates an automated execution system where 
the special representative is always the contra side to each transaction. 
• Clears for a [[Broker]]/dealer who operates an automated execution system where the [[Broker]]/dealer is 
always the contra side to each transaction, and the subscribers to the automated execution system 
enter into an agreement with the [[Broker]]/dealer and the Special Representative acknowledging the 
Special Representative's role in the clearance of trades executed on the automated execution system. 
Overview of the FIX Message Protocol 
The Financial Information eXchange (FIX) protocol is a series of messaging specifications for the electronic 
communication of trade-related messages. FIX is a self-describing protocol that’s similar in many ways to other 
self-describing protocols, such as HTML. The FIX session is layered on TCP (Transmission Control Protocol).

Message Format 
The UTC data feed comprises a series of variable-length sequenced messages following the FIX version 4.4 
conventions. FIX messages are formed from several fields; each field is a tag/value pairing that is separated 
from the next field by a delimiter Start of Heading (SOH) (0x01). The tag is a string representation of an integer 
that indicates the meaning of the field. The value is an array of bytes that holds a specific meaning for a tag. 
FIX also defines sets of fields that make a message; within each set some fields will be mandatory, and others 
will be optional. 
The message is broken into three distinct sections: header, body, and trailer. Fields must remain within the 
correct section. Within each section the position may be important because fields can act as delimiters that 
stop one message from running into the next. The final field in any FIX message is TAG 10 (checksum). 
There are two main groups of messages: administrative and application. Administrative messages handle the 
basics of a FIX session. They allow for a session to be started and terminated and for the recovery of missed 
messages. Application messages deal with the sending and receiving of trade-related information, such as a 
trade contract message.  
FIX Engine Input 
[[NSCC]] expects to receive all trades for a sending entity on a single FIX session, and the good-night message 
associated with the sending entity also needs to be submitted to the same FIX session. [[NSCC]] uses this 
information to facilitate the end-of-day/good-night processing.  
Multiple sending entities could be included in a single FIX session, if the associated good-night messages are 
sent to the same FIX session. A sending entity is used to define a "balancing unit" that is used at end of day to 
verify the count of messages sent from the exchange to [[NSCC]]. Each FIX session corresponds to a sending 
entity. If an exchange requires multiple sessions, it is responsible to divide the traffic between the sessions and 
assign the correct sending entity for data sent over that session.  
For marketplaces operating two sites, only one site is considered the primary site at any time, and only the 
primary site should be sending trade data. The second site could be sending heartbeats but cannot send new 
or duplicate trade data for the same sending entity. In the case of a marketplace fail-over when the secondary 
site becomes the primary site, [[NSCC]] begins receiving trade data from the 'new primary' session. Accordingly, 
the good night message for the associated sending entry is to be received from the 'new primary' session 
allowing [[NSCC]]'s end-of-day processing to begin.

FIX Repeating Groups 
The UTC FIX format uses two repeating groups to identify trading parties and fees. The field that indicates how 
many repeating groups are in a set must equal the number of groups entered in the transaction. UTC utilizes 
two repeating groups for [[Broker]] detail (tag 453) and fee information (tag 136). For example, tag 453 identifies 
the number of submitted [[Broker]] party roles. The value entered in this field must equal the total number of buy 
and sell tag 448/tag 452 groups that follow. Differences in the group identifier value and the number of groups 
submitted for the transaction, or submissions of group [[ID]]’s for the buy and sell side, will result in a rejected 
trade record.  
Message Queue (MQ) Input 
Message Queue (MQ) input to [[NSCC]] leverages the tag-based UTC FIX format, with some minor differences 
outlined in the following pages. MQ input submitters can group up to 30 transactions into a single message. A 
time component should be considered in this process. If transactions [[DO]] not group in sufficient time to 
constitute real-time submission to [[NSCC]], the available transactions should be sent. Group transactions should 
be separated by tag 10 (checksum) or a delimiter X’03’. For example, a firm should send the blocked trade 
message when one of the following conditions occurs: 
• 30 trades have been added to a block. 
• x seconds have elapsed without additional trades to add to the block. (x = a configurable parameter – 
such as 1 - 3 seconds). In this case, the blocked trade message would be sent with the number of 
transactions that accrued to that point, between 1 and 29.

SUBMISSION NOTES 
Tag Sequence Requirements 
UTC requires trade capture message sections to be submitted in the following sequence: 1) header, 2) trade 
capture data and 3) trailer. 
Within the trade capture data section, UTC requires certain fields to be submitted sequentially: 
1. Tag 22 (Security [[ID]] Source) must precede tag 48 (ISIN/[[CUSIP]]). 
2. Several UTC fields (tags 1 (Account [[ID]]), 11 (Client Order [[ID]]), 37 (Order [[ID]]), 66 (Execution [[ID]]), 198 
(Market Control Number), 526 (Original Execution [[ID]]), 528 (Order Capacity) and 825 ([[Liquidity]] Indicator)) 
follow special treatment as they are present for both the “buy” and “sell” side on UTC input formats. The 
first instance of these tags will be identified as the “buy” side. The second instance will be identified as the 
“sell” side. For example, if only one tag 11 is submitted, UTC will identify it as the “[[Buyer]]” field and will 
produce it on output to the “[[Buyer]]”. One method to ensure proper passage of data, if only the sell side 
value is known, is to put zero (“0”) in the first instance of tags 1, 11, 37, 66, 198, 526, 528 and 825, then 
on the second instance input the known “[[Seller]]” value.  
3. Tag 453 (NoPartyIDs) must precede the following tag 448/452 (Party information and roles) fields. 
4. Tag 136 (NoMiscFees) must precede the following tag 137/139 (Fee information) fields. 
5. Tag 552 (Number of sides) must precede the first tag 54 (Buy indicator). 
6. Tag 54 (Side Indicator): 
a. [[NSCC]] requires tag 54 to be submitted on input, with the Buy Indicator first and Sell Indicator second. 
Valid, defined values must be submitted for each. Failure to meet these requirements will result in a 
rejected trade record. 
b. All Buy side fields must be grouped together and must be submitted separately from the sell side 
fields.  
c. Each grouping should begin with the side’s respective tag 54 (Side indicator). 
7. Tag 10 must be the last field on all messages.

Record Format Rules – Blank Fields 
To comply with FIX protocol standards, [[NSCC]] does not report blank fields/tags in FIX or MQ messages.

[[NSCC]] utilizes the “Sending Entity” field (tag 115) on the Universal Trade Capture input formats to identify the

Rejected Trades  
UTC creates the following two types of invalid trade records:  
• Hard rejects (rejects)  
• Soft rejects (pends) 
Accepted, Rejected and Pended transactions are identified by the [[NSCC]] Reject Code field (FIX tag 751, UTC 
MRO position 426-427). 
Hard Rejects (Rejects) 
Hard rejects are rejected trades for which subsequent revalidation will not be attempted. Examples of hard 
rejects are trades with invalid quantity, price or trade date. Trades with duplicate trade sequence numbers are 
identified as “hard” rejects and are processed as such.  
Soft Rejects (Pends) 
Pends are trades for which subsequent revalidation will be attempted. Trades deemed as pends have either 
invalid [[Broker]] or security information, or both. Revalidation of the pended items occurs periodically throughout 
the same day of submission. If accepted, these trades are reported to clearing firms as regular accepted 
trades. If failed, they are pended until the next successful revalidation attempt or the last revalidation 
processing cycle of the day. 
During the last revalidation processing cycle of the day, all remaining pended trades are deemed hard rejects 
and are reported to effected clearing firms and markets. The last revalidation of the day occurs when the last 
market Good Night message is received.

Step In – Step Out Rule 
The UTC record format includes a Step In – Step Out indicator (FIX tag #81). Possible values include: 
• 0 - Regular 
• 2 - Step In 
• 3 - Step Out 
The UTC formats include one step-in / step-out indicator on the trade input record. The sending entity must 
provide UTC with the [[Seller]]’s data about the submitted step-in / step-out value. UTC will process the step-in / 
step-out information received from the market and assign an opposite transaction to the contra-[[Broker]].

Good Night Processing for Clearing Firms, Markets, and UTC 
The following good night processing applies: 
1. At the end of the processing day, markets and other sending entities send their Good Night trade totals to 
UTC. Submission of a Good Night message signifies to [[NSCC]] the end of day and closure of the sending 
entities input stream. 
2. UTC balances these totals with each market and sends a confirmation message to each sending entity. 
3. UTC sends a Good Night message to clearing firms indicating trade totals as each market closes.  
4. When all markets are closed, UTC sends a final Good Night message to clearing firms indicating UTC is 
closed for this processing day. 
Clearing firm and markets that transmit data via messages (MQ or FIX) will receive all messages described 
above. Those who receive MRO files [[DO]] not receive Good Night notification as each market closes. The UTC 
Contract MRO includes an indicator that notes that the UTC application is closed for the day. 
For more information about good night formats, see the UTC Input/Output Message Formats section of the 
[[DTCC]] Learning Center.

Price Variance Reporting 
UTC provides a price variance indicator to notify clearing firms when a trade differs significantly from the 
market price.

When Issued (WI) / When Distributed Processing 
When issued transactions are generally defined as transactions in a security which have occurred prior to the 
issuance (or for when-distributed, the distribution) of such security. The designation of a transaction as being 
“when-issued or when-distributed” is determined by the marketplace or exchange on which the security trades. 
Such trades are reported to clearing firms with the [[settlement]] date of 12/31/9999 until a [[settlement]] date is 
assigned to the issue. 
Daily, the WI trades are validated against the Security Master Database to determine if a [[settlement]] date has 
been assigned. WI [[securities]] are usually ‘peeled’ two days before [[settlement]]. 
The UTC application generates three daily files of WI trades: 
1. When Issued Totals MRO - Contains the WI trades’ totals by clearing firm (buy and sell), market, ISIN and 
the ISIN’s projected [[settlement]] date (if known). 
2. When Issued Peeled [[securities]] MRO - Contains a listing of [[securities]] (by ISIN) that were ‘peeled’, 
announcing the [[settlement]] date for this issue. Two days before [[settlement]] date, when issued security 
[[settlement]] date information is added to this file and is distributed to subscribing clearing firms who have 
transactions in effected security. This information is not available on the UTC Print Image Report. 
3. The When-Issued Intraday Peeled [[securities]] MRO reports non-cumulative when issued peels (i.e. 
[[settlement]] date announcements) earlier in the day. This MRO is issued twice per day, at 10:00 AM and 
3:00 PM, and only includes security peels that occurred in the period since the prior file was distributed. 
The file layout for this new MRO matches that of the current, cumulative end of day WI Peel MRO 
(Autoroute #02080982) file.

Automated Special Representative Facility (CORR and QSR) 
[[NSCC]] has implemented an online facility by which clearing firms themselves may establish, monitor and

this message. For information about the [[Broker]] Cease to Act formats, see the Equities Clearing – Universal
